# 工作流总览 / Workflow Overview

> 本文件规定**接口、契约、断点与安全语义**。
> 照此实现，任何团队都能搭出自己的适配器与编排器，并与他人的实现互相校验结果。

---

## 1. 要解决的问题

上游是一个包含大量技能（SKILL.md）的仓库。**逐个读没问题，串起来跑立刻卡住**，
而且卡得没有声音。审计 601 个技能得到的分布：

| 事实 | 数量 |
| --- | --- |
| 技能总数 | 601 |
| 实测验证可执行（`verified=true`） | **1** |
| 纯提示词技能（无可执行入口） | **201** |
| 未声明输入格式 | **401** |
| 入口未文档化 | **202** |
| 声明依赖但未声明版本 | 346 |

**结论**：这类技能库的价值是**知识**，不是**可执行流程**。
把它当自动化用，会在第一个阶段撞墙——而且是静默地撞。

因此本工作流的定位是：

> **一个知道什么时候该停下来问人的编排层，而不是一个全自动产品。**

## 2. 五阶段流水线

```
S1 生成          S2 处理          S3 分析           S4 出图            S5 报告
SimulatedDataset → CleanDataset → AnalysisResult → FigureArtifact → ReportBundle
      │                │               │                │                │
      └── 每个交接点：契约校验 + 四级判定 + 失败回滚 + 必要时结构化人工介入 ──┘
```

阶段之间**只通过契约对话**。每个阶段声明：

| 声明项 | 含义 |
| --- | --- |
| `contract_in` / `contract_out` | 输入/输出的契约类型 |
| `producer` | 谁能产出它（技能 / 适配器 / 生成器 / 人工） |
| `requires` | 前置阶段 |
| `on_human_intervention` | 遇到断点时的默认动作 |
| `failure_rollback` | 失败时清理什么 + **如何验证上游未被破坏** |

## 3. 统一信封（13 字段）

五份契约共用同一个信封，这样编排器与审计工具只需要处理一种外层结构：

| 组 | 字段 | 约束 |
| --- | --- | --- |
| 身份 | `id` | 必填。格式 `stage-slug-hex`，**确定性派生**（同输入同 id） |
| | `source_skill` | 必填。非技能产出时用 `generator:NAME` / `human:NAME` |
| | `source_skill_path` | 技能在仓库中的相对路径 |
| | `stage` | `S1_simulate` / `S2_process` / `S3_analyze` / `S4_figure` / `S5_report` |
| 形态 | `format` | 实际涉及的格式族数组 |
| | `schema_version` | 信封版本 |
| | `payload` | 各阶段自己的载荷（见 contracts.md） |
| 审计 | `provenance` | 血缘链，见下 |
| | `human_interventions` | 关联的断点请求 id 列表 |
| | `notes` | 人类可读备注 |
| 时间 | `created_at` / `updated_at` | UTC、带时区 |
| 扩展 | `metadata` | 校验报告、执行记录、决策痕迹 |

**硬约束**：`id` 与 `source_skill` 必填，其余字段不得为未知值——未声明一律写 `TODO`，**不得编造**。

## 4. 血缘（provenance）

每一步记录一个 `ProvenanceStep`：

| 字段 | 含义 |
| --- | --- |
| `kind` | `skill` / `adapter` / `human` / … |
| `ref` | 该步的引用名（技能 id 或适配器模块名） |
| `adapter` | 执行该步的适配器 |
| `inputs` | **上游契约 id 列表** —— 血缘链靠它串起来 |
| `params` | 该步的关键参数（列映射、技能 id、模式等） |
| `at` | 时刻 |
| `note` | 备注 |

审计要求：**从任一产物都能沿 `inputs` 回溯到最初的模拟数据**。

## 5. 幂等语义

同一输入重复执行，**产出必须逐字节相同**，且**内容未变时不得重写文件**。

实现要点（这是最容易做错的地方）：

- 落盘内容里**不能包含"本次执行的时刻"**。若包含，则两次执行内容必然不同，
  于是文件每次都被重写，幂等声明形同虚设；
- 正确做法：把落盘时刻**锚定到对象自身派生出的确定性时刻**，
  使"同一输入 → 同一内容 → 不重写"成立；
- 保险层：落盘前若已存在一份"除时间戳外完全相同"的文件，**沿用其原有时间戳**。

> ⚠️ 陷阱：某些文件系统（如 exFAT）文件时间戳粒度只有 **2 秒**，
> 会把"其实每次都在重写"伪装成"mtime 没变"。**幂等测试必须同时比对内容字节，不能只看 mtime。**

## 6. 编排器职责边界

编排器**只做编排**：按序调用 → 记录 → 失败回滚 → 汇总。转换逻辑全部在适配器里，
这样编排层与适配器层可以各自独立测试。

本蓝本的失败回滚语义里含一步**验证** —— 回滚不只是删文件，还要确认上游没被动过：

| 阶段 | 回滚动作 | 验证 |
| --- | --- | --- |
| 任意阶段 | 删除本阶段契约副本与临时产物 | **上游契约文件指纹与执行前一致** |
| 出图阶段 | 只删契约副本，**不删图形文件** | 图形文件数量与运行前一致 |
| 报告阶段 | 删除报告与契约副本 | 上游契约仍存在且可校验通过 |

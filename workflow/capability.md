## 1. 上游技能库的实测分布

| 事实 | 数量 | 占比 |
| --- | --- | --- |
| 技能总数 | 601 | 100% |
| 实测验证可执行 | **1** | 0.2% |
| 纯提示词技能（无可执行入口） | **201** | 33% |
| 未声明输入格式 | **401** | 67% |
| 入口未文档化 | **202** | 34% |
| 声明依赖但未声明版本 | 346 | 58% |
| 非上游作者的第三方署名技能 | 3 | 已移除 |

**能自动执行的只有 1 个。** 这不是本工作流的缺陷，而是这类技能库的真实形态：
它们的价值是**知识**，不是**可执行流程**。

## 2. 本工作流能做什么

- 五阶段协议驱动的端到端流水线
- 每阶段失败回滚，且**验证上游未被破坏**
- 幂等：内容未变不重写文件；同输入产出逐字节相同
- 四级断点判定 + 九种原因码的结构化人工介入
- 安全接口：致命故障即刻切断
- 出图支持两条通道：本地兜底（不依赖外部运行时）与上游原生技能（质量更高）

## 3. 本工作流做不到什么

| 限制 | 说明 |
| --- | --- |
| **绝大多数技能无法自动执行** | 601 个里只有 1 个通过实测验证 |
| **三分之一是纯提示词** | 201 个技能**永远无法**接入自动流水线 |
| 图型覆盖有限 | 上游有大量制图技能，实际验证并接入的只是少数 |
| 平台承诺窄 | 已在 Windows x64 + CPython 3.10 实测；其他平台架构上无障碍但**未实测** |
| 需要人工补齐数据 | 大量技能未声明输入格式，需要人工提供列映射或结构化数据 |

## 4. 本蓝本不适用的场景

这些不是"正确用法"的规训，而是**我们在自己的场景里划的边界** —— 你的场景不同，结论可能完全不同：

| 场景 | 为什么本蓝本不适用 |
| --- | --- |
| 期望"全自动跑完不问人" | 本蓝本会在大量断点处停下 —— **停下正是设计意图** |
| 用真实患者数据 | 契约层的合成数据约束会直接拒绝；本项目定位是方法验证，不是临床数据处理 |
| 把 `degraded` 请求当成功继续 | 降级结果会被当成正常结果往下传（`strict` 策略能拦住这类） |
| 绕过 `verified` 门禁直接执行技能 | 未验证技能的失败方式不可预期，排查成本很高 |

## 5. 设计立场

> 这类项目的价值**不在于让多少技能跑起来，而在于把"跑不起来的那些"变成
> 有结构、有证据、有人能处理的断点。**
>
> 一个诚实的"这里需要人"，比一个静默的错误结果值钱得多。

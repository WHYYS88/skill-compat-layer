# 安全接口规格 / Safety Interface

## 1. 它解决什么问题

> **哪些故障属于"再跑下去就是错的"？**

很多编排器只做到"停止本阶段"。但**"停止本阶段"和"不让下游拿到坏数据"是两件不同的事**：
上游契约已经坏了或数据不可信时，继续进入下一阶段只会产出不可信的结果，
并且污染下游产物。

安全接口（熔断器）把这件事显式化：命中致命故障时**即刻切断**，
后续阶段一律不再执行，并把故障码、阶段与证据写入运行报告。

## 2. 三态策略

| 策略 | 行为 | 适用 |
| --- | --- | --- |
| `off` | 关闭切断，但**留痕**（报告中 `enabled=false`） | 调试；**绝不静默不设防** |
| `default` | 只对"接口失效 / 数据不可信"切断 | 常规运行 |
| `strict` | 额外对"降级冒充"切断 | 结果将进入申报/发表等强审计场景 |

**优先级链**：`CLI 开关` > `环境变量` > `配置文件` > `默认值`（`default`）。

## 3. 故障分类

### 硬停（`default` 即切断）

| 原因码 | 为什么致命 |
| --- | --- |
| `payload_schema_mismatch` | 契约字段对不上 = **接口已失效** |
| `unsupported_transformation` | 做不了的转换，再跑也无意义 |
| `data_quality_blocker` | 数据本身不可用 |
| `ambiguous_semantics` | 语义未定，下游可能误读 |

### 仅 `strict` 切断（"降级冒充"风险）

| 原因码 | 风险 |
| --- | --- |
| `renderer_unavailable` | 高精度通道不可用却用兜底图顶替，外观看不出差别 |
| `dependency_undeclared` / `entry_not_documented` / `prompt_only_skill` / `format_undeclared` | 能力边界不清 |

> 本蓝本把"降级冒充"单独归成了一类。它值得单独讨论：同样是"继续跑"，一个是数据缺一半，
> 一个是精度被悄悄换掉，后者从产物上根本看不出来。

## 4. 四类触发源

| 触发源 | 检查内容 |
| --- | --- |
| 结构化断点 | 断点原因码是否命中硬停清单；`degraded` 级只在 `strict` 下触发 |
| 未捕获异常 | 最典型的致命故障 —— 立即切断 |
| 上游契约完整性 | 文件是否还在；**本阶段执行期间是否被改写**（指纹比对） |
| 产出契约自检 | 能否通过 `validate()`；产出格式与下游声明**是否有交集** |

## 5. 实现时踩到的两个坑

本蓝本早期版本的真实记录 —— 列出来是因为这类错误很隐蔽，而且代价大：

| 我们当时怎么写的 | 后果 | 后来改成 |
| --- | --- | --- |
| 把"本阶段自己的输出目录"当作上游 | 正常流程被判 `upstream_missing`，**误熔断** | 上游 = **之前阶段产出的契约文件** |
| 用契约 id 去比对按阶段名索引的字典 | 正常流程被判血缘断裂 | 血缘由契约自带的 `provenance` 表达，不重复判定 |

> 两次都是端到端实跑才发现的 —— 单测覆盖不到"正常流程会不会被误伤"。
> 我们现在的自检顺序是：**先用正常路径跑一遍确认不误报**，再看它该报的时候报不报。
> 一个会误伤正常流程的熔断器，比没有熔断器更难排查。

## 6. 报告字段

运行报告中的 `circuit_breaker` 段：

| 字段 | 含义 |
| --- | --- |
| `policy` | 本次生效的策略 |
| `enabled` | 是否启用（`off` 时为 false） |
| `tripped` | 是否已切断 |
| `checks_run` | 执行过的检查次数 |
| `fault` | 触发时的 `{code, stage, detail, evidence, policy}` |
| `stop_reasons` | 本次生效的硬停原因码清单 |
